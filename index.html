PROCESO PR-001

Cálculo de pagos, saldos y cobros

Construye una tabla temporal de cuotas de un crédito, distribuye abonos, calcula los componentes dinámicos de capital e intereses y determina los días de mora y el interés moratorio de las cuotas con saldo pendiente.

1.0

3.1. Identificación del proceso

Tipo PROCEDIMIENTO ALMACENADO
Plataforma IBM INFORMIX SPL
Frecuencia NO ESPECIFICADA
Transaccionalidad NO ESPECIFICADA

3.2. Parámetros de entrada

Nombre Tipo de dato Descripción Obligatorio
pNit VARCHAR(30) Identificador del cliente o entidad utilizado para filtrar los registros relacionados con el crédito. No especificado
pTipoDocumento CHAR(4) Tipo de documento utilizado para identificar el crédito en las consultas. No especificado
pNumeroDocumento BIGINT Número del documento asociado al crédito. No especificado

3.5. Desglose paso a paso

  1. Preparación de la tabla temporal

    Propósito: Preparar una estructura de trabajo para almacenar las cuotas que serán procesadas

    Variables: temp_tabladepagos

    Operaciones: Se elimina la tabla temporal si existe y posteriormente se crea con columnas para identificación del crédito, saldos, cuotas, vencimientos, abonos e intereses

    Efectos: Se reinicia la estructura temporal utilizada por el procedimiento

  2. Lectura de parámetros de cálculo

    Propósito: Obtener los parámetros que intervienen en los cálculos de intereses

    Variables: vsol_dias_int y vinf_dias_anuales

    Operaciones: se consulta t_pagos_parametro mediante SELECT LIMIT 1 para recuperar la cantidad de días de interés y la base anual

    Condiciones: El código no muestra una validación explícita para el caso en que la consulta no proporcione los parámetros esperados

  3. Obtención de vencimientos y cuotas

    Propósito: Determinar las cuotas iniciales que serán incluidas en la tabla temporal

    Variables: vFechaMaxima y vAbono

    Operaciones: Se obtiene MAX(f_vence) desde sdocs utilizando el NIT, tipo de documento, número, cuenta, ano_mesd igual a cero y cuota mayor que cero. Si la fecha máxima es NULL, se asigna pFechaCalculo

    Resultado: Se insertan las cuotas que cumplen los filtros y cuya fecha de vencimiento no supera vFechaMaxima

  4. Obtención del saldo inicial y la tasa corriente

    Propósito: Recuperar los valores de referencia para el cálculo dinámico de las cuotas

    Variables: vsaldo_doc, vretencion, vmsaldo_inicial_prestamo, vmcuota, vsaldo_doc_restante y vtasa_int

    Operaciones: se consulta docs para obtener el saldo del documento, la retención y el valor inicial. También se consulta sdocs para obtener el saldo de la cuota número dos

    Cálculo: vsaldo_doc_restante se inicializa con la suma del saldo del documento y la retención, sustituyendo valores NULL por cero

    Dependencia: fn_informa_trae_i_corriente proporciona la tasa de interés corriente del crédito

  5. Identificación de la última formalización

    Propósito: Establecer la referencia temporal y el identificador de movimiento a partir de los comprobantes de formalización

    Variables: vFechaUltimaFormalizacion y vIdUltimaFormalizacion

    Condición: Primero se busca la fecha máxima y el ID máximo de movimientos positivos asociados a comprobantes de tipo SOL

    Rama alternativa: Si la fecha obtenida es NULL, se consulta la formalización CAS

    Observación: En la segunda consulta CAS se asigna MAX(fecha) a vIdUltimaFormalizacion. Debe verificarse si debería utilizarse MAX(id_movi)

  6. Cálculo del último pago y los abonos

    Propósito: Identificar el último pago registrado y determinar el importe disponible para aplicarlo a las cuotas

    Variables: vFechaUltimoPago, vFechaUltimaFormalizacion, vIdUltimaFormalizacion y vAbono

    Operaciones: Se obtiene la fecha máxima de movimientos positivos con comprobantes RC o SOL. Si no existe, se utiliza la fecha de formalización

    Reglas: Se excluyen los comprobantes SOL y CAS del cálculo de abonos. Los movimientos cuya descripción coincide con %INT%COR% reciben un factor de cero. El signo del importe depende de deb_cre

    Resultado: Si la suma calculada es NULL, vAbono se establece en cero

  7. Obtención de la configuración de mora

    Propósito: Identificar si existe una tabla de pagos modificada y obtener los parámetros utilizados para calcular la mora

    Variables: vse_modifico_tp, v_iva_mora y vcobro_mora

    Operaciones: Se consulta tpagos para el crédito. Después se obtiene la tasa mediante fn_informa_trae_tasa_mora

    Condición: Si la tasa obtenida es NULL, se convierte en cero. Si es cero, se consulta concaja para recuperar tasa_iva

    Resultado: inf_parametro proporciona inf_calculo_mora, que interviene en la fórmula de interés moratorio

  8. Distribución de abonos y recálculo de cuotas

    Propósito: Actualizar los saldos de las cuotas y calcular los componentes dinámicos de capital e interés

    Variables: vAbono, vsaldosdocs, vcuota, vmcuota, vminteres, vmcapital_cuota y vsaldo_doc_restante

    Primera condición: Si vAbono es mayor o igual que el saldo de la cuota, se resta dicho saldo del abono y se establece el saldo de la cuota en cero

    Segunda condición: Cuando el abono no cubre el saldo, se calcula el interés según la modalidad de la tabla de pagos

    Tabla modificada: Se calculan los días de interés modificados a partir de vmint_cuota, vinf_dias_anuales, el saldo inicial y vtasa_int

    Tabla no modificada: Para la primera cuota se utiliza la diferencia entre el vencimiento y la fecha de formalización. Para las demás cuotas se utiliza vsol_dias_int

    Control de capital: El interés se limita al valor de la cuota. El capital se calcula restando el interés. Si el capital es negativo, se establece en cero. Si supera el saldo restante, se limita al saldo

    Efectos: Se actualizan saldo_sdoc, debed_dynamico y haberd_dynamico. Cuando vAbono es mayor que cero en esta rama, el código lo establece posteriormente en cero

3.6. Reglas de negocio

  • RN-001: Las cuotas iniciales se seleccionan de sdocs con ano_mesd igual a cero y cuota mayor que cero
  • RN-002: Cuando no se encuentra una formalización SOL, se busca una formalización CAS
  • RN-003: Cuando no se obtiene la fecha del último pago, se utiliza la fecha de formalización como referencia
  • RN-004: El cálculo de abonos excluye movimientos con descripciones que coinciden con el patrón %INT%COR%
  • RN-005: Si el abono disponible cubre el saldo de la cuota, el saldo se establece en cero y el importe del saldo se resta del abono disponible
  • RN-006: El interés calculado no puede superar el valor de la cuota según la validación implementada
  • RN-007: El capital calculado no puede ser negativo. Si supera el saldo restante del documento, se limita a dicho saldo
  • RN-008: Se generan cuotas adicionales con saldo cero cuando la última fecha de vencimiento es anterior a pFechaCalculo y la fecha generada sigue siendo estrictamente menor que la fecha de cálculo.
  • RN-009: El interés moratorio se actualiza únicamente para cuotas con saldo positivo y días de mora mayores que cero.
  • RN-010: La tasa de mora se obtiene primero mediante fn_informa_trae_tasa_mora. Si resulta cero, se consulta la tasa_iva de concaja.

3.10. Notas y limitaciones

Nota técnica

El procedimiento realiza el procesamiento mediante una tabla temporal denominada temp_tabladepagos. Las operaciones de actualización descritas afectan esa estructura temporal. El código suministrado no muestra una persistencia final de los resultados en una tabla permanente ni un SELECT final que devuelva el detalle de las cuotas

Advertencias

En la rama alternativa CAS, la consulta asigna MAX(fecha) a vIdUltimaFormalizacion, variable declarada como INT. Además, la consulta no obtiene MAX(id_movi). Debe verificarse esta inconsistencia antes de modificar o validar el comportamiento

Validación pendiente

Antes de considerar validada esta documentación, se recomienda probar créditos con abonos parciales, abonos que cubren cuotas completas, tablas de pago modificadas, ausencia de formalización SOL, formalización CAS, cuotas vencidas y cuotas posteriores a la última fecha de vencimiento. También debe verificarse el cálculo de interés moratorio con los parámetros reales

3.5. Desglose paso a paso

  1. Preparación de la tabla temporal

    Propósito: Preparar una estructura de trabajo para almacenar las cuotas que serán procesadas

    Variables: temp_tabladepagos

    Operaciones: Se elimina la tabla temporal si existe y posteriormente se crea con columnas para identificación del crédito, saldos, cuotas, vencimientos, abonos e intereses

    Efectos: Se reinicia la estructura temporal utilizada por el procedimiento

  2. Lectura de parámetros de cálculo

    Propósito: Obtener los parámetros que intervienen en los cálculos de intereses

    Variables: vsol_dias_int y vinf_dias_anuales

    Operaciones: se consulta t_pagos_parametro mediante SELECT LIMIT 1 para recuperar la cantidad de días de interés y la base anual

    Condiciones: El código no muestra una validación explícita para el caso en que la consulta no proporcione los parámetros esperados

  3. Obtención de vencimientos y cuotas

    Propósito: Determinar las cuotas iniciales que serán incluidas en la tabla temporal

    Variables: vFechaMaxima y vAbono

    Operaciones: Se obtiene MAX(f_vence) desde sdocs utilizando el NIT, tipo de documento, número, cuenta, ano_mesd igual a cero y cuota mayor que cero. Si la fecha máxima es NULL, se asigna pFechaCalculo

    Resultado: Se insertan las cuotas que cumplen los filtros y cuya fecha de vencimiento no supera vFechaMaxima

  4. Obtención del saldo inicial y la tasa corriente

    Propósito: Recuperar los valores de referencia para el cálculo dinámico de las cuotas

    Variables: vsaldo_doc, vretencion, vmsaldo_inicial_prestamo, vmcuota, vsaldo_doc_restante y vtasa_int

    Operaciones: se consulta docs para obtener el saldo del documento, la retención y el valor inicial. También se consulta sdocs para obtener el saldo de la cuota número dos

    Cálculo: vsaldo_doc_restante se inicializa con la suma del saldo del documento y la retención, sustituyendo valores NULL por cero

    Dependencia: fn_informa_trae_i_corriente proporciona la tasa de interés corriente del crédito

  5. Identificación de la última formalización

    Propósito: Establecer la referencia temporal y el identificador de movimiento a partir de los comprobantes de formalización

    Variables: vFechaUltimaFormalizacion y vIdUltimaFormalizacion

    Condición: Primero se busca la fecha máxima y el ID máximo de movimientos positivos asociados a comprobantes de tipo SOL

    Rama alternativa: Si la fecha obtenida es NULL, se consulta la formalización CAS

    Observación: En la segunda consulta CAS se asigna MAX(fecha) a vIdUltimaFormalizacion. Debe verificarse si debería utilizarse MAX(id_movi)

  6. Cálculo del último pago y los abonos

    Propósito: Identificar el último pago registrado y determinar el importe disponible para aplicarlo a las cuotas

    Variables: vFechaUltimoPago, vFechaUltimaFormalizacion, vIdUltimaFormalizacion y vAbono

    Operaciones: Se obtiene la fecha máxima de movimientos positivos con comprobantes RC o SOL. Si no existe, se utiliza la fecha de formalización

    Reglas: Se excluyen los comprobantes SOL y CAS del cálculo de abonos. Los movimientos cuya descripción coincide con %INT%COR% reciben un factor de cero. El signo del importe depende de deb_cre

    Resultado: Si la suma calculada es NULL, vAbono se establece en cero

  7. Obtención de la configuración de mora

    Propósito: Identificar si existe una tabla de pagos modificada y obtener los parámetros utilizados para calcular la mora

    Variables: vse_modifico_tp, v_iva_mora y vcobro_mora

    Operaciones: Se consulta tpagos para el crédito. Después se obtiene la tasa mediante fn_informa_trae_tasa_mora

    Condición: Si la tasa obtenida es NULL, se convierte en cero. Si es cero, se consulta concaja para recuperar tasa_iva

    Resultado: inf_parametro proporciona inf_calculo_mora, que interviene en la fórmula de interés moratorio

  8. Distribución de abonos y recálculo de cuotas

    Propósito: Actualizar los saldos de las cuotas y calcular los componentes dinámicos de capital e interés

    Variables: vAbono, vsaldosdocs, vcuota, vmcuota, vminteres, vmcapital_cuota y vsaldo_doc_restante

    Primera condición: Si vAbono es mayor o igual que el saldo de la cuota, se resta dicho saldo del abono y se establece el saldo de la cuota en cero

    Segunda condición: Cuando el abono no cubre el saldo, se calcula el interés según la modalidad de la tabla de pagos

    Tabla modificada: Se calculan los días de interés modificados a partir de vmint_cuota, vinf_dias_anuales, el saldo inicial y vtasa_int

    Tabla no modificada: Para la primera cuota se utiliza la diferencia entre el vencimiento y la fecha de formalización. Para las demás cuotas se utiliza vsol_dias_int

    Control de capital: El interés se limita al valor de la cuota. El capital se calcula restando el interés. Si el capital es negativo, se establece en cero. Si supera el saldo restante, se limita al saldo

    Efectos: Se actualizan saldo_sdoc, debed_dynamico y haberd_dynamico. Cuando vAbono es mayor que cero en esta rama, el código lo establece posteriormente en cero

3.6. Reglas de negocio

  • RN-001: Las cuotas iniciales se seleccionan de sdocs con ano_mesd igual a cero y cuota mayor que cero
  • RN-002: Cuando no se encuentra una formalización SOL, se busca una formalización CAS
  • RN-003: Cuando no se obtiene la fecha del último pago, se utiliza la fecha de formalización como referencia
  • RN-004: El cálculo de abonos excluye movimientos con descripciones que coinciden con el patrón %INT%COR%
  • RN-005: Si el abono disponible cubre el saldo de la cuota, el saldo se establece en cero y el importe del saldo se resta del abono disponible
  • RN-006: El interés calculado no puede superar el valor de la cuota según la validación implementada
  • RN-007: El capital calculado no puede ser negativo. Si supera el saldo restante del documento, se limita a dicho saldo
  • RN-008: Se generan cuotas adicionales con saldo cero cuando la última fecha de vencimiento es anterior a pFechaCalculo y la fecha generada sigue siendo estrictamente menor que la fecha de cálculo.
  • RN-009: El interés moratorio se actualiza únicamente para cuotas con saldo positivo y días de mora mayores que cero.
  • RN-010: La tasa de mora se obtiene primero mediante fn_informa_trae_tasa_mora. Si resulta cero, se consulta la tasa_iva de concaja.

3.5. Desglose paso a paso

  1. Preparación de la tabla temporal

    Propósito: Preparar una estructura de trabajo para almacenar las cuotas que serán procesadas

    Variables: temp_tabladepagos

    Operaciones: Se elimina la tabla temporal si existe y posteriormente se crea con columnas para identificación del crédito, saldos, cuotas, vencimientos, abonos e intereses

    Efectos: Se reinicia la estructura temporal utilizada por el procedimiento

  2. Lectura de parámetros de cálculo

    Propósito: Obtener los parámetros que intervienen en los cálculos de intereses

    Variables: vsol_dias_int y vinf_dias_anuales

    Operaciones: se consulta t_pagos_parametro mediante SELECT LIMIT 1 para recuperar la cantidad de días de interés y la base anual

    Condiciones: El código no muestra una validación explícita para el caso en que la consulta no proporcione los parámetros esperados

  3. Obtención de vencimientos y cuotas

    Propósito: Determinar las cuotas iniciales que serán incluidas en la tabla temporal

    Variables: vFechaMaxima y vAbono

    Operaciones: Se obtiene MAX(f_vence) desde sdocs utilizando el NIT, tipo de documento, número, cuenta, ano_mesd igual a cero y cuota mayor que cero. Si la fecha máxima es NULL, se asigna pFechaCalculo

    Resultado: Se insertan las cuotas que cumplen los filtros y cuya fecha de vencimiento no supera vFechaMaxima

  4. Obtención del saldo inicial y la tasa corriente

    Propósito: Recuperar los valores de referencia para el cálculo dinámico de las cuotas

    Variables: vsaldo_doc, vretencion, vmsaldo_inicial_prestamo, vmcuota, vsaldo_doc_restante y vtasa_int

    Operaciones: se consulta docs para obtener el saldo del documento, la retención y el valor inicial. También se consulta sdocs para obtener el saldo de la cuota número dos

    Cálculo: vsaldo_doc_restante se inicializa con la suma del saldo del documento y la retención, sustituyendo valores NULL por cero

    Dependencia: fn_informa_trae_i_corriente proporciona la tasa de interés corriente del crédito

  5. Identificación de la última formalización

    Propósito: Establecer la referencia temporal y el identificador de movimiento a partir de los comprobantes de formalización

    Variables: vFechaUltimaFormalizacion y vIdUltimaFormalizacion

    Condición: Primero se busca la fecha máxima y el ID máximo de movimientos positivos asociados a comprobantes de tipo SOL

    Rama alternativa: Si la fecha obtenida es NULL, se consulta la formalización CAS

    Observación: En la segunda consulta CAS se asigna MAX(fecha) a vIdUltimaFormalizacion. Debe verificarse si debería utilizarse MAX(id_movi)

  6. Cálculo del último pago y los abonos

    Propósito: Identificar el último pago registrado y determinar el importe disponible para aplicarlo a las cuotas

    Variables: vFechaUltimoPago, vFechaUltimaFormalizacion, vIdUltimaFormalizacion y vAbono

    Operaciones: Se obtiene la fecha máxima de movimientos positivos con comprobantes RC o SOL. Si no existe, se utiliza la fecha de formalización

    Reglas: Se excluyen los comprobantes SOL y CAS del cálculo de abonos. Los movimientos cuya descripción coincide con %INT%COR% reciben un factor de cero. El signo del importe depende de deb_cre

    Resultado: Si la suma calculada es NULL, vAbono se establece en cero

  7. Obtención de la configuración de mora

    Propósito: Identificar si existe una tabla de pagos modificada y obtener los parámetros utilizados para calcular la mora

    Variables: vse_modifico_tp, v_iva_mora y vcobro_mora

    Operaciones: Se consulta tpagos para el crédito. Después se obtiene la tasa mediante fn_informa_trae_tasa_mora

    Condición: Si la tasa obtenida es NULL, se convierte en cero. Si es cero, se consulta concaja para recuperar tasa_iva

    Resultado: inf_parametro proporciona inf_calculo_mora, que interviene en la fórmula de interés moratorio

  8. Distribución de abonos y recálculo de cuotas

    Propósito: Actualizar los saldos de las cuotas y calcular los componentes dinámicos de capital e interés

    Variables: vAbono, vsaldosdocs, vcuota, vmcuota, vminteres, vmcapital_cuota y vsaldo_doc_restante

    Primera condición: Si vAbono es mayor o igual que el saldo de la cuota, se resta dicho saldo del abono y se establece el saldo de la cuota en cero

    Segunda condición: Cuando el abono no cubre el saldo, se calcula el interés según la modalidad de la tabla de pagos

    Tabla modificada: Se calculan los días de interés modificados a partir de vmint_cuota, vinf_dias_anuales, el saldo inicial y vtasa_int

    Tabla no modificada: Para la primera cuota se utiliza la diferencia entre el vencimiento y la fecha de formalización. Para las demás cuotas se utiliza vsol_dias_int

    Control de capital: El interés se limita al valor de la cuota. El capital se calcula restando el interés. Si el capital es negativo, se establece en cero. Si supera el saldo restante, se limita al saldo

    Efectos: Se actualizan saldo_sdoc, debed_dynamico y haberd_dynamico. Cuando vAbono es mayor que cero en esta rama, el código lo establece posteriormente en cero

3.6. Reglas de negocio

  • RN-001: Las cuotas iniciales se seleccionan de sdocs con ano_mesd igual a cero y cuota mayor que cero
  • RN-002: Cuando no se encuentra una formalización SOL, se busca una formalización CAS
  • RN-003: Cuando no se obtiene la fecha del último pago, se utiliza la fecha de formalización como referencia
  • RN-004: El cálculo de abonos excluye movimientos con descripciones que coinciden con el patrón %INT%COR%
  • RN-005: Si el abono disponible cubre el saldo de la cuota, el saldo se establece en cero y el importe del saldo se resta del abono disponible
  • RN-006: El interés calculado no puede superar el valor de la cuota según la validación implementada
  • RN-007: El capital calculado no puede ser negativo. Si supera el saldo restante del documento, se limita a dicho saldo
  • RN-008: Se generan cuotas adicionales con saldo cero cuando la última fecha de vencimiento es anterior a pFechaCalculo y la fecha generada sigue siendo estrictamente menor que la fecha de cálculo.
  • RN-009: El interés moratorio se actualiza únicamente para cuotas con saldo positivo y días de mora mayores que cero.
  • RN-010: La tasa de mora se obtiene primero mediante fn_informa_trae_tasa_mora. Si resulta cero, se consulta la tasa_iva de concaja.

3.10. Notas y limitaciones

Nota técnica

El procedimiento realiza el procesamiento mediante una tabla temporal denominada temp_tabladepagos. Las operaciones de actualización descritas afectan esa estructura temporal. El código suministrado no muestra una persistencia final de los resultados en una tabla permanente ni un SELECT final que devuelva el detalle de las cuotas

Advertencias

En la rama alternativa CAS, la consulta asigna MAX(fecha) a vIdUltimaFormalizacion, variable declarada como INT. Además, la consulta no obtiene MAX(id_movi). Debe verificarse esta inconsistencia antes de modificar o validar el comportamiento

Validación pendiente

Antes de considerar validada esta documentación, se recomienda probar créditos con abonos parciales, abonos que cubren cuotas completas, tablas de pago modificadas, ausencia de formalización SOL, formalización CAS, cuotas vencidas y cuotas posteriores a la última fecha de vencimiento.     Efectos: Se reinicia la estructura temporal utilizada por el procedimiento

  2. Lectura de parámetros de cálculo

    Propósito: Obtener los parámetros que intervienen en los cálculos de intereses

    Variables: vsol_dias_int y vinf_dias_anuales

    Operaciones: se consulta t_pagos_parametro mediante SELECT LIMIT 1 para recuperar la cantidad de días de interés y la base anual

    Condiciones: El código no muestra una validación explícita para el caso en que la consulta no proporcione los parámetros esperados

  3. Obtención de vencimientos y cuotas

    Propósito: Determinar las cuotas iniciales que serán incluidas en la tabla temporal

    Variables: vFechaMaxima y vAbono

    Operaciones: Se obtiene MAX(f_vence) desde sdocs utilizando el NIT, tipo de documento, número, cuenta, ano_mesd igual a cero y cuota mayor que cero. Si la fecha máxima es NULL, se asigna pFechaCalculo

    Resultado: Se insertan las cuotas que cumplen los filtros y cuya fecha de vencimiento no supera vFechaMaxima

  4. Obtención del saldo inicial y la tasa corriente

    Propósito: Recuperar los valores de referencia para el cálculo dinámico de las cuotas

    Variables: vsaldo_doc, vretencion, vmsaldo_inicial_prestamo, vmcuota, vsaldo_doc_restante y vtasa_int

    Operaciones: se consulta docs para obtener el saldo del documento, la retención y el valor inicial. También se consulta sdocs para obtener el saldo de la cuota número dos

    Cálculo: vsaldo_doc_restante se inicializa con la suma del saldo del documento y la retención, sustituyendo valores NULL por cero

    Dependencia: fn_informa_trae_i_corriente proporciona la tasa de interés corriente del crédito

  5. Identificación de la última formalización

    Propósito: Establecer la referencia temporal y el identificador de movimiento a partir de los comprobantes de formalización

    Variables: vFechaUltimaFormalizacion y vIdUltimaFormalizacion

    Condición: Primero se busca la fecha máxima y el ID máximo de movimientos positivos asociados a comprobantes de tipo SOL

    Rama alternativa: Si la fecha obtenida es NULL, se consulta la formalización CAS

    Observación: En la segunda consulta CAS se asigna MAX(fecha) a vIdUltimaFormalizacion. Debe verificarse si debería utilizarse MAX(id_movi)

  6. Cálculo del último pago y los abonos

    Propósito: Identificar el último pago registrado y determinar el importe disponible para aplicarlo a las cuotas

    Variables: vFechaUltimoPago, vFechaUltimaFormalizacion, vIdUltimaFormalizacion y vAbono

    Operaciones: Se obtiene la fecha máxima de movimientos positivos con comprobantes RC o SOL. Si no existe, se utiliza la fecha de formalización

    Reglas: Se excluyen los comprobantes SOL y CAS del cálculo de abonos. Los movimientos cuya descripción coincide con %INT%COR% reciben un factor de cero. El signo del importe depende de deb_cre

    Resultado: Si la suma calculada es NULL, vAbono se establece en cero

  7. Obtención de la configuración de mora

    Propósito: Identificar si existe una tabla de pagos modificada y obtener los parámetros utilizados para calcular la mora

    Variables: vse_modifico_tp, v_iva_mora y vcobro_mora

    Operaciones: Se consulta tpagos para el crédito. Después se obtiene la tasa mediante fn_informa_trae_tasa_mora

    Condición: Si la tasa obtenida es NULL, se convierte en cero. Si es cero, se consulta concaja para recuperar tasa_iva

    Resultado: inf_parametro proporciona inf_calculo_mora, que interviene en la fórmula de interés moratorio

  8. Distribución de abonos y recálculo de cuotas

    Propósito: Actualizar los saldos de las cuotas y calcular los componentes dinámicos de capital e interés

    Variables: vAbono, vsaldosdocs, vcuota, vmcuota, vminteres, vmcapital_cuota y vsaldo_doc_restante

    Primera condición: Si vAbono es mayor o igual que el saldo de la cuota, se resta dicho saldo del abono y se establece el saldo de la cuota en cero

    Segunda condición: Cuando el abono no cubre el saldo, se calcula el interés según la modalidad de la tabla de pagos

    Tabla modificada: Se calculan los días de interés modificados a partir de vmint_cuota, vinf_dias_anuales, el saldo inicial y vtasa_int

    Tabla no modificada: Para la primera cuota se utiliza la diferencia entre el vencimiento y la fecha de formalización. Para las demás cuotas se utiliza vsol_dias_int

    Control de capital: El interés se limita al valor de la cuota. El capital se calcula restando el interés. Si el capital es negativo, se establece en cero. Si supera el saldo restante, se limita al saldo

    Efectos: Se actualizan saldo_sdoc, debed_dynamico y haberd_dynamico. Cuando vAbono es mayor que cero en esta rama, el código lo establece posteriormente en cero

3.6. Reglas de negocio

  • RN-001: Las cuotas iniciales se seleccionan de sdocs con ano_mesd igual a cero y cuota mayor que cero
  • RN-002: Cuando no se encuentra una formalización SOL, se busca una formalización CAS
  • RN-003: Cuando no se obtiene la fecha del último pago, se utiliza la fecha de formalización como referencia
  • RN-004: El cálculo de abonos excluye movimientos con descripciones que coinciden con el patrón %INT%COR%
  • RN-005: Si el abono disponible cubre el saldo de la cuota, el saldo se establece en cero y el importe del saldo se resta del abono disponible
  • RN-006: El interés calculado no puede superar el valor de la cuota según la validación implementada
  • RN-007: El capital calculado no puede ser negativo. Si supera el saldo restante del documento, se limita a dicho saldo
  • RN-008: Se generan cuotas adicionales con saldo cero cuando la última fecha de vencimiento es anterior a pFechaCalculo y la fecha generada sigue siendo estrictamente menor que la fecha de cálculo.
  • RN-009: El interés moratorio se actualiza únicamente para cuotas con saldo positivo y días de mora mayores que cero.
  • RN-010: La tasa de mora se obtiene primero mediante fn_informa_trae_tasa_mora. Si resulta cero, se consulta la tasa_iva de concaja.

    Operación: Después de terminar el FOREACH, se agregan los caracteres ]}} para cerrar el arreglo y los objetos externos

3.5. Desglose paso a paso

  1. Declaración de variables

    Propósito: Preparar las variables para almacenar los campos consultados, controlar las excepciones y construir la respuesta JSON

    Variables: vNit, vTipo_Doc, vNumero_Doc, vCentro_Costo, vMonto_Pagar, vCodigo_Pago, vComprobante, vNumero, vComma, vCodError, vISAMValue, vTextoResultado, vObjeto y vResultado

    Efecto: Se establecen los tipos de datos y las capacidades de almacenamiento para el procedimiento

  2. Identificación del objeto

    Propósito: Identificar el procedimiento para utilizar esa referencia en los mensajes de error

    Operación: Se asigna el texto pa_dar_info_transaccion a vObjeto

    Resultado: La variable queda disponible para la construcción del mensaje alternativo del manejador de excepciones

  3. Configuración del manejo de excepciones

    Propósito: Capturar información de una excepción durante la ejecución

    Operación: El bloque ON EXCEPTION asigna los datos capturados a vCodError, vISAMValue y vTextoResultado

    Condición: Si el texto del error está vacío después de aplicar LENGTH(TRIM(vTextoResultado)), se asigna un mensaje alternativo

    Resultado: Se intenta retornar una cadena JSON que representa el error

  4. Inicialización de la respuesta

    Propósito: Preparar la estructura inicial del JSON de éxito

    Variables: vComma y vResultado

    Operaciones: Se establece el separador en una cadena vacía y se inicia la respuesta con las propiedades Resultado, Codigo y Data.data

    Resultado: La cadena queda preparada para recibir los registros

  5. Consulta de la transacción

    Propósito: Recuperar los datos de la transacción solicitada y los datos relacionados del pago

    Tablas: t_cajas_transaccion_pago y t_pagos_pago

    Operaciones: Se realiza un LEFT JOIN mediante b.codigo_pago = a.codigo_pago. La consulta filtra los registros mediante codigo_transaccion = pcodigo_transaccion

    Resultado: Los campos seleccionados se almacenan en las ocho variables correspondientes

  6. Normalización de algunos valores NULL

    Propósito: Proporcionar valores alternativos para determinados campos de la consulta

    Operaciones: centro_costo y comprobante utilizan una cadena vacía cuando el valor es NULL. Los campos codigo_pago y numero utilizan cero

    Limitación: Esta normalización no se aplica explícitamente a todas las columnas consultadas

  7. Construcción de los objetos JSON

    Propósito: Convertir cada registro recuperado en un objeto representado mediante una cadena JSON

    Variables: vResultado y vComma, junto con las variables que contienen los datos de la transacción

    Operaciones: Se concatenan las propiedades nit, tipo_doc, numero_doc, centro_costo, monto, comprobante, numero y codigo_pago

    Separación: El primer objeto se agrega sin una coma inicial. Después de cada objeto, vComma se establece como una coma para separar los registros siguientes

  8. Cierre y retorno de la respuesta

    Propósito: Completar la estructura del JSON y devolverla al proceso que invocó el procedimiento

    Operación: Después de terminar el FOREACH, se agregan los caracteres ]}} para cerrar el arreglo y los objetos externos

    Resultado: Se ejecuta RETURN vResultado, cuyo tipo declarado es CHAR(31000)

3.6. Reglas de negocio

  • RN-001: La consulta se filtra utilizando el código de transacción recibido en pcodigo_transaccion.
  • RN-002: Los registros de t_pagos_pago se relacionan mediante un LEFT JOIN con t_cajas_transaccion_pago.
  • RN-003: Si centro_costo es NULL, se utiliza una cadena vacía.
  • RN-004: Si codigo_pago o numero es NULL, se utiliza cero.
  • RN-005: Cada registro recuperado se representa como un objeto dentro del arreglo Data.data.
  • RN-006: El separador de los objetos JSON se controla mediante la variable vComma.
  • RN-007: El procedimiento declara un manejador de excepciones que intenta devolver información sobre el error.
  • RN-008: El código no implementa explícitamente una respuesta de error de negocio cuando la consulta no devuelve registros.

3.10. Notas y limitaciones

Nota técnica

El procedimiento construye manualmente una cadena JSON mediante concatenación. La respuesta de éxito contiene las propiedades Resultado, Codigo y Data, dentro de la cual existe un arreglo data con los registros encontrados

Advertencias

La concatenación de valores NULL puede afectar el resultado. También deben controlarse las comillas, barras invertidas y otros caracteres especiales de los campos de texto para evitar JSON inválido. La expresión NVL(vCodigo_Pago, '') utiliza un valor alternativo de tipo texto para una variable numérica y debe corregirse o verificarse. El manejador de excepciones también debe revisarse porque la estructura JSON de error puede quedar mal formada

La cláusula WHERE utiliza codigo_transaccion sin calificarla con el alias a. Es recomendable utilizar a.codigo_transaccion para explicitar la tabla de origen

Validación

La documentación se elaboró a partir del código proporcionado. No se ha ejecutado el procedimiento contra una base de datos Informix. Queda pendiente validar la sintaxis en el entorno real, el comportamiento con transacciones inexistentes, los valores NULL, los errores de ejecución y la validez del JSON generado
